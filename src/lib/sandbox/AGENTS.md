- Long Context Generation stores everything in the separate "vision-sandbox" D1 (binding SANDBOX_DB via `db.server.ts`, REST fallback off-Worker); the main "vision" D1 is never touched. `generation.ts` is pure (plan, waves, context layers, checksum, validation); `store.server.ts` owns owner-scoped SQL with CAS transitions and idempotent inserts; `runner.server.ts` runs plan → parallel waves → assemble → validate via `orchestrateText`, resumable from persisted state. Why: temporary output generation is isolated from production data and every step survives crashes without duplicating work.
- Runners persist unexpected failures and settle parallel work before termination; assembly checks the full plan and saved checksums, and in-run retries reset only their own failed chunk. Why: recovery cannot steal active work or silently deliver missing sections.
- Prompt-generation workspace (migration 0005) lives in `workspace.ts`: store-agnostic functions taking a Db, every call scoped by server-derived userId; it reuses `generation_jobs` (prompt state in `workflow_status`) and `generation_events` (= job_events). Cleanup runs only from the Worker cron via /api/internal/sandbox-cleanup and deletes rows of one job at a time, never the main "vision" D1. Why: additive, testable on SQLite, isolation-safe.
- Cloudflare story jobs mirror into the prompt workspace via `story-workspace.server.ts` (idempotency key `runtime:<jobId>`, chat from the owner-scoped jobs row); every write is failure-tolerant; after the runtime job is `completed` and `replyPersisted` confirms the reply in main D1, `cleanupNow` purges that job immediately (CAS-claimed, idempotent), else data is kept and the hourly sweep is only the fallback. Why: the slot runner stays the single engine and workspace issues never break delivery.
